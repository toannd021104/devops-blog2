> Đây là bản gộp đầy đủ của loạt bài mình ghi lại khi làm workshop **Building Agents on Amazon EKS**. Xuyên suốt loạt bài, mình xây một customer service agent cho AnyCompany Shop và bồi thêm một khả năng mới sau mỗi phần. Thứ tự trình bày dưới đây đi theo mạch mình thấy dễ hiểu nhất: dựng agent → đưa tool ra MCP → quan sát bằng trace → siết bảo mật → hiểu gateway → và cuối cùng là chạy code trong sandbox.

Sáu phần, sáu khả năng chồng lên nhau:

| Phần | Khả năng | Agent hưởng lợi gì |
| --- | --- | --- |
| 1. First agent | Core loop | Nhận query, suy luận, gọi tool, trả lời |
| 2. Tools với MCP | Tool trên mạng | Dời tool ra MCP server, khám phá lúc runtime |
| 3. Observability | Trace | Nhìn xuyên mọi LLM call và tool call trong Langfuse |
| 4. Securing | Phân quyền | Ép per-tool access theo persona đã đăng nhập |
| 5. The AI Gateway | Control point | Hiểu endpoint model mà mọi thứ đi qua |
| 6. Sandbox | Chạy code an toàn | Đẩy code không tin cậy sang microVM cô lập |

# Phần 1 — Building your first agent

> Deploy agent đầu tiên cho AnyCompany Shop, xây bằng **Strands Agents SDK**. Lời gọi model của nó tới Amazon Bedrock qua Envoy AI Gateway.

## Kiến trúc

<Image src={img18} alt="First agent flow: query từ Chainlit UI tới Strands Agent, OpenAI wire format tới Envoy AI Gateway, Converse API với SigV4 Pod Identity tới Bedrock, và tool lookup_order đọc DynamoDB" />

Agent không bao giờ gọi Bedrock trực tiếp và không giữ credential Bedrock. Nó gửi một request chat-completions bình thường tới gateway, và gateway sở hữu AWS identity (SigV4 qua EKS Pod Identity) rồi dịch sang Converse API của Bedrock. Đổi model (Nova sang Claude) là đổi một dòng `MODEL_ID`, không phải đổi code.

> **💡 Giải thích:** Agent chính là vòng lặp: nhận câu hỏi → hỏi model → nếu model bảo "gọi tool" thì gọi → đưa kết quả lại cho model → trả lời khách.

### Strands SDK là gì?

Một Python SDK mã nguồn mở để xây agent. LLM quyết định gọi tool nào và theo thứ tự nào. Bốn khái niệm gánh cả SDK:

- **Agent**: vòng lặp gửi message tới LLM và thực thi tool call
- **Model**: bất kỳ endpoint nào nói chat-completions API. Ở đây là Envoy AI Gateway trước Bedrock
- **Tools**: hàm Python gắn decorator `@tool` mà agent có thể gọi
- **System prompt**: chỉ dẫn định hình hành vi agent

### Code walkthrough

Mọi giá trị đến từ environment, nên cùng một image chạy ở đâu cũng được:

```python
model_base_url = os.environ.get("MODEL_BASE_URL", "http://localhost:4000/v1")

model = OpenAIModel(
    client_args={
        "base_url": model_base_url,
        "api_key": os.environ.get("MODEL_API_KEY", "not-needed"),
    },
    model_id=os.environ.get("MODEL_ID", "nova-lite"),
    params={"max_tokens": 1024, "temperature": 0.3},
)
```

- `base_url`: `MODEL_BASE_URL` trỏ tới Envoy AI Gateway, cấp bởi ConfigMap `agent-config`.
- `api_key="not-needed"`: gateway tự xác thực với Bedrock bằng identity của nó qua Pod Identity.
- `model_id="nova-lite"`: một alias mà gateway rewrite sang model id Bedrock thật.

> **💡 Giải thích:** Cả ba giá trị đều đọc từ biến môi trường chứ không hardcode — nguyên tắc 12-factor: cấu hình tách khỏi code.

### Deploy to EKS

`k8s.yaml` là một Deployment cộng một ClusterIP Service ở port 8080. Hai chi tiết wiring gánh việc nặng:

- `serviceAccountName: agent` cấp quyền truy cập DynamoDB qua Pod Identity (cho `lookup_order`)
- `envFrom: agent-config` là ConfigMap đưa `MODEL_BASE_URL`, `MODEL_ID`, `ORDERS_TABLE` vào container tự động

Image ref dùng placeholder, nên render bằng `envsubst` trước khi apply:

```bash
cd ~/environment/modules/200-strands-agents/customer-agent
envsubst < k8s.yaml | kubectl apply -f -
kubectl rollout status deployment/customer-agent --timeout=120s
```

# Phần 2 — Agent tools với MCP

> Đến giờ mọi tool đều sống bên trong process của agent. Ở phần này mình dời tool ra một MCP server độc lập mà agent khám phá lúc runtime, và định tuyến mọi tool call qua **agentgateway**.

### MCP là gì?

**Model Context Protocol** là một chuẩn mở để expose tool cho agent qua mạng. Một MCP server publish một tập tool; một MCP client (ở đây là Strands agent) kết nối, gọi `list_tools` để khám phá cái gì có sẵn, và gọi chúng theo tên. Agent không import code tool; nó học tool lúc runtime từ server.

> **💡 Giải thích:** Trước đây tool là "hàm nằm trong người agent". Với MCP, tool trở thành "dịch vụ chạy riêng trên mạng" mà agent gọi qua giao thức chuẩn.

**Bốn thứ bạn được khi đưa tool lên mạng:**

- **Decoupled**: logic tool ở một chỗ, đổi một lần thay vì phải roll ra mọi agent nhúng nó.
- **Discoverable**: thêm tool vào server và agent nhặt nó ở lần connect kế tiếp.
- **Shareable**: nhiều agent dùng chung một tool server.
- **Một control point**: một proxy ở giữa (agentgateway) thấy và phân quyền từng tool call.

### agentgateway là gì?

Tool call đi qua **agentgateway**, một MCP gateway: proxy nói được giao thức, nên thấy được từng operation `tools/list` và `tools/call`. Đó là thứ làm cho per-tool authorization khả thi.

```bash

```

### Code walkthrough

<details>
<summary><strong>mcp-server/server.py — định nghĩa tool</strong></summary>

```python
mcp = FastMCP(
    "AnyCompany Tools",
    transport_security=TransportSecuritySettings(enable_dns_rebinding_protection=False),
)

@mcp.tool()
def lookup_order(order_id: str) -> dict:
    """Look up order status, tracking, and details by order ID."""
    ...

@mcp.tool()
def check_inventory(product_name: str) -> dict:
    """Check stock availability for a product."""
    ...
```

FastMCP biến hàm Python thường thành MCP tool. Decorator `@mcp.tool()` là bản đối ứng phía server của `@tool` bên Strands. Server chạy như `streamable_http_app()` trên port 8080.
</details>

<details>
<summary><strong>Forward token của user theo session</strong></summary>

MCP server ngồi sau agentgateway, cái này (ở phần Securing) phân quyền mỗi tool call theo Cognito persona của caller, nên tool call phải mang identity của user:

```python
# server.py: rút token đã forward, dựng/cache agent theo session
access_token = authorization[7:] if authorization.lower().startswith("bearer ") else None
agent = _get_session_agent(req.session_id, access_token)

# agent.py: MCP client của session connect KÈM token đó
headers = {"Authorization": f"Bearer {access_token}"} if access_token else None
client = MCPClient(lambda u=url: streamablehttp_client(u, headers=headers))
```
</details>

> **💡 Giải thích:** Vì mỗi user có token riêng, agent không thể là một instance dùng chung toàn cục. Mỗi phiên chat tạo một agent riêng mang token của chính user đó.

# Phần 3 — Observability với Langfuse

> Agent hiện là hộp đen: khi trả lời chậm hoặc sai, bạn không thấy được model call hay tool invocation nào gây ra. Ở phần này mình instrument agent bằng OpenTelemetry và đọc trace trong Langfuse.

Hai thành phần đã chạy sẵn trong cluster: Langfuse và một OpenTelemetry Collector chung mà mọi workload export tới.

```bash
kubectl get pods,svc -n telemetry
kubectl get pods -n langfuse
```

<Image src={img20} alt="Pods và service trong namespace telemetry và langfuse" />

> **💡 Giải thích:** Trace là bản ghi chi tiết một request đi qua những đâu, mất bao lâu mỗi chặng. Với agent AI, trace cho thấy model đã quyết định gọi tool nào, tốn bao nhiêu token, chặng nào chậm.

### Khác gì so với phần trước

Code agent gần như giống hệt. Ba thứ được thêm để trace chảy:

- Một Langfuse client trong `agent.py` xác thực lúc khởi động và flush span sau mỗi request.
- OpenTelemetry auto-instrumentation trong image (Dockerfile chạy app bằng `opentelemetry-instrument`, patch `httpx` và FastAPI mà không đổi code).
- Export target: ConfigMap `agent-config` set `OTEL_EXPORTER_OTLP_ENDPOINT` tới collector chung.

> **💡 Giải thích:** Bạn gần như **không viết thêm code** để có tracing. `opentelemetry-instrument` tự "chèn" đo đạc vào các thư viện có sẵn lúc chạy — auto-instrumentation.

### Vì sao span của gateway nằm chung một trace

Header `traceparent` là phần quan trọng. Envoy AI Gateway đọc nó ở mỗi request, nên span của nó lồng dưới trace của agent thay vì bắt đầu một trace riêng.

# Phần 4 — Securing the agents

> Ở phần MCP, agent bắt đầu forward Cognito token của user trên mỗi tool call, nhưng không gì kiểm tra nó. Cả hai persona đều gọi được mọi tool. Ở phần này mình biến token đó thành access control thật.

### Hai persona, quyền khác nhau

| Persona | Group | Được phép |
| --- | --- | --- |
| Support Associate | support-associate | Tra cứu đơn và xử lý trả hàng |
| Sales Analyst | sales-analyst | Chỉ tra cứu đơn |

| Tool | Cho phép với | Lý do |
| --- | --- | --- |
| lookup_order | Cả hai persona | Read-only, dùng chung |
| initiate_return | Chỉ Support Associate | Thay đổi một đơn |
| check_inventory | Không ai, ở lab này | Minh họa deny-by-default |

> **💡 Giải thích:** Chia làm hai lớp: **authentication** (anh là ai) và **authorization** (anh được làm gì). Cả hai đặt ở gateway, nên agent hoàn toàn không biết gì về bảo mật.

<details>
<summary><strong>Authentication (mcp-authn) gắn vào Gateway</strong></summary>

```yaml
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayPolicy
metadata:
  name: mcp-authn
  namespace: agentgateway-system
spec:
  targetRefs:
    - kind: Gateway
      name: agentgateway
      group: gateway.networking.k8s.io
  traffic:
    jwtAuthentication:
      mode: Strict            # không token, không vào
      providers:
        - issuer: __COGNITO_ISSUER__
          audiences:
            - __COGNITO_CLIENT_ID__
          jwks:
            remote:
              backendRef:
                group: agentgateway.dev
                kind: AgentgatewayBackend
                name: cognito-jwks
                namespace: agentgateway-system
                port: 443
              jwksPath: __COGNITO_JWKS_PATH__
```

Token thiếu hoặc không hợp lệ bị từ chối 401 trước khi bất kỳ logic tool nào chạy.
</details>

<details>
<summary><strong>Authorization (mcp-tool-authz) gắn vào backend</strong></summary>

```yaml
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayPolicy
metadata:
  name: mcp-tool-authz
  namespace: default
spec:
  targetRefs:
    - kind: AgentgatewayBackend
      name: mcp-backend
      group: agentgateway.dev
  backend:
    mcp:
      authorization:
        action: Allow
        policy:
          matchExpressions:
            - 'false'         # match không gì: deny-all của Step A
```

`matchExpressions` là thứ duy nhất đổi qua ba bước; mọi thứ phía trên giữ nguyên.
</details>

> **💡 Giải thích:** `action: Allow` nhưng biểu thức `'false'` (không match gì) lại **cấm tất cả**, vì agentgateway là **deny-by-default**.

# Phần 5 — The AI Gateway

> Mọi lời gọi model đến giờ đều đi qua Envoy AI Gateway. Phần này dừng lại để hiểu rõ endpoint đó: platform team dựng nó trước Bedrock để giải quyết ba câu hỏi — ai giữ credential, ai quản tên model, ai thấy được chi phí.

## Kiến trúc tổng thể

# Phần 6 — Agents using a sandbox

> Các tool tới giờ trả lời câu hỏi cố định. Nhưng một Sales Analyst hỏi câu mở như "vẽ biểu đồ doanh số tháng trước theo region". Model cần viết code, chạy nó trên nhiều đơn, và hiện kết quả — an toàn.

Mỗi lần thực thi có một máy ảo dùng-một-lần riêng, tạo qua **Kata Containers** với **Firecracker**. VM air-gapped, không mạng không credential, và bị huỷ sau một lần chạy. Runtime class tên `kata-fc`.

> **💡 Giải thích:** Code do LLM sinh ra là **không đáng tin**. Giải pháp không phải kiểm duyệt code cho kỹ, mà chạy nó ở một nơi cô lập hoàn toàn: không mạng để tuồn dữ liệu, không credential để trộm, và bị xoá sạch sau mỗi lần.

### Prerequisites

```bash
kubectl rollout status deployment/mcp-server
kubectl get agentgatewaypolicy mcp-authn -n agentgateway-system
```

<Image src={img51} alt="Xác nhận hai prerequisites" />

### The isolation model

`run_python` không thực thi code trong agent. Nó gọi một broker (MCP server `code-executor`) mà: fetch một lát đơn có scope, claim một `kata-fc` microVM tươi, ghi row và code sinh ra vào đó thành file, chạy code, đọc lại kết quả, và huỷ microVM.

<details>
<summary><strong>Broker làm gì mỗi call</strong></summary>

Mỗi call, broker:

- dựng một DynamoDB query có scope, tham số hoá từ tham số đã validate,
- fetch lát đơn có giới hạn đó (broker giữ read-only creds),
- claim một `kata-fc` microVM pre-warmed từ pool và ghi row + code sinh ra vào đó thành file,
- chạy code, đọc lại stdout và chart nếu có, rồi huỷ microVM.

Pool là lý do việc này đủ nhanh để ngồi sau một tin nhắn chat.
</details>

<details>
<summary><strong>Hai tính chất làm nó an toàn</strong></summary>

- **microVM air-gapped.** NetworkPolicy của nó set `egress: []` và nó mount không ServiceAccount token.
- **Dữ liệu vào out-of-band.** Row đơn ghi vào microVM thành file (`/app/orders.json`), không truyền qua LLM. Model viết code trên một schema được mô tả.
</details>

<details>
<summary><strong>Giữ chart ngoài đường LLM</strong></summary>

- `run_python` → broker → microVM: code lưu `/app/chart.png`
- broker đọc PNG lại, cache, trả về một `chart_id` ngắn cho agent
- agent fetch PNG từ broker (`GET /chart/{id}`) và stream tới UI
- UI render chart inline

Model chỉ bao giờ thấy một `chart_id`, không bao giờ ảnh base64.
</details>

> **💡 Giải thích:** Cả dữ liệu vào lẫn ảnh ra đều đi "đường vòng" (out-of-band), không qua LLM. Vừa tiết kiệm token, vừa giữ raw data ngoài context model.
